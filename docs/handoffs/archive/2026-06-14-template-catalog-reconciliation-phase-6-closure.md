## Two findings the plan did NOT anticipate (READ THIS)

### Finding 1 — `estimate-catalog.json` is NOT a pure harvest artifact; sync-codes would clobber it

The plan's Phase 6 step said "re-run `npm run sync-codes`; `estimate-catalog.json`
is re-harvested." In reality the committed `estimate-catalog.json` has **227**
entries = **221 harvested + 6 architect-confirmed manual built-in additions
(2026-06-10)**: `03-3543.002` Sealed Concrete, `07-1000.003` Tuckpointing,
`09-9000.002` Painting-Exterior, `26-0000.006` Electrical-Generator,
`32-1613.007` Concrete Curb Stops, `01-0230.002` SAC Determination. These 6 live
directly in the JSON and are **not** in the template's STEP 4 sheet, so
`npm run sync-codes` regenerates the JSON at 221 and **destroys them** — which
would also break `catalogPriceLookup.test.ts:52` and `catalogRateSeed.test.ts:79`
(both pin 227), violating the "tests green" exit criterion.

**Decision:** `estimate-catalog.json` was **deliberately left at HEAD (227), not
re-committed.** The Importer-sheet edit provably does not affect the catalog
harvest (the catalog is built from STEP 4 + Budget Line Items, never the Importer
sheet), so "unchanged" is the correct Phase 6 outcome for that file. The 6-entry
re-harvest drop is a pre-existing property of how the file is maintained, not a
Phase 6 change. **Caveat for the future:** anyone who runs `npm run sync-codes`
must restore `estimate-catalog.json` to keep the 6 manual additions (or those 6
should be migrated into a non-clobbered overlay — a possible cleanup, out of
scope here). `scripts/output/cost-code-gaps.json` was likewise restored to HEAD
(its only re-harvest diff was the `generatedAt` timestamp; `invalidProcoreCodes`
stayed 0).

### Finding 2 — removing the 7 dead codes aligned Importer ≡ Budget Line Items (217 ≡ 217)

The 7 dead codes were **exactly** the codes present in the Importer set but absent
from the Budget Line Items sheet. Removing them makes the two sets identical (217
each). A good outcome — but it obsoletes one `export-integrity.test.ts` fixture
that used `2-20000.000` as a "valid Procore code missing from the BLI sheet, so it
exercises the BLI-append branch." No such code exists anymore, so the exporter's
(correct) guard now rejects appending `2-20000.000`. The fixture (`div02Row`) was
repointed to **`4-40000.000`** (Masonry division base — valid, has a BLI row, div
≥ 04 so untouched by the GC/Site-Ops zero-writes), and the test reframed from
"appends missing mapped codes" to "writes computed values … for every mapped
code." **Note:** the exporter's append-of-a-valid-missing-code branch is now
defensive-only and no longer covered by a real-template test; restoring dedicated
coverage via the synthetic template fixture is an optional follow-up.
